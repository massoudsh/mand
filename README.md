# ماند (Mand)

[![CI](https://github.com/massoudsh/mand/actions/workflows/ci.yml/badge.svg)](https://github.com/massoudsh/mand/actions/workflows/ci.yml)

**ماند — جایی خرج کن که واقعاً اثر می‌کند.**
*Mand — Spend your growth budget where it actually works.*

موتور هوشمند تصمیم‌گیری نگهداشت (Retention)، Uplift و بهینه‌سازی مشوق برای پلتفرم‌های مصرفی ایرانی.

## مسئله

پلتفرم‌های مصرفی ایرانی بودجه‌ی زیادی روی پیام و تخفیف خرج می‌کنند، اما نمی‌دانند کدام مداخله
incremental value می‌سازد و کدام فقط margin می‌سوزاند. `churn prediction` می‌گوید چه کسی در
خطر است؛ سؤال درست‌تر این است که **روی چه کسی مداخله واقعاً اثر دارد**.

## راه‌حل

ماند به‌جای فقط پیش‌بینی churn، برای هر کاربر uplift هر مداخله (پیام، push، تخفیف، cashback) را
تخمین می‌زند، هزینه‌ی incentive را در نظر می‌گیرد و تصمیم می‌دهد:

- روی چه کسی مداخله کن
- از چه کانالی
- چه زمانی
- با چه نوع و مقدار مشوقی
- و کجا **اصلاً بودجه‌ای خرج نکن**
- **چرا** — هر تصمیم با دلیل قابل‌فهم همراه است (Explainability Engine)، نه فقط یک عدد

## بازار هدف

GrowthTech سازمانی — مارکت‌پلیس‌ها، فین‌تک‌ها و اپ‌های مصرفی ایرانی که بودجه‌ی واقعی روی
retention و incentive خرج می‌کنند و ROI برایشان حیاتی است.

## نقشه راه

جزئیات کامل فازها در [ROADMAP.md](./ROADMAP.md) و issueها/milestoneهای گیت‌هاب.

## وضعیت

پروژه در فاز ۰ (اکتشاف و انتخاب design partner) است. یک MVP دمو با دادهٔ مصنوعیِ واقع‌نما، API و داشبورد تصمیم RTL برای اعتبارسنجی قرارداد داده و تجربهٔ محصول در اختیار است. نسخهٔ ۰.۳.۰ پنج قابلیت پرتکرار بازار (سفر مشتری، هاب کانال، کیف پول مشوق، مرکز آزمایش و زمان ارسال) را به‌صورت محاسباتی و شبیه‌سازی‌شده اضافه کرده است.

## اجرای MVP

نیازمندی: Node.js 20.20.2 و Python 3.12 با SQLite استاندارد؛ بدون dependency اجرایی npm.

```bash
npm ci
npm run db:migrate
npm run db:seed
npm run lint
npm run test:coverage
npm run build
npm start
```

`build` فقط سه فایل static را در `dist/` کپی می‌کند؛ UI به backend همان دامنه نیاز دارد. سرور از `frontend/` سرو می‌کند. شروع سرور migration و seed غیرمخرب را هم اجرا می‌کند. تست‌ها DB واقعی موقت می‌سازند و پاک می‌کنند؛ دادهٔ دمو در `db/mand.sqlite` می‌ماند و به Git نمی‌رود. schema در `db/schema.sql` و bridge تراکنشی SQLite در `db/store.py` است. این bridge همگام برای دمو کم‌ترافیک است، نه استقرار پرترافیک.

### اجرا با Docker

ایمیج بر پایهٔ `node:20.20.2-bookworm-slim` است و Python 3.11 (فقط کتابخانهٔ استاندارد) را برای bridge نصب می‌کند. برنامه با کاربر غیرroot اجرا می‌شود، فایل SQLite در volume مسیر `/data` می‌ماند و healthcheck از `/api/ready` استفاده می‌کند.

```bash
docker build -t mand:0.3.0 .
docker run -d --name mand -p 3000:3000 \
  -e MAND_APPROVER_KEY="<at-least-32-characters>" \
  -v mand-data:/data \
  mand:0.3.0
```

یا با Compose:

```bash
cp .env.example .env   # سپس MAND_APPROVER_KEY را پر کنید
docker compose up -d --build
```

- `MAND_DB_PATH` در ایمیج روی `/data/mand.sqlite` تنظیم شده است؛ volume را حذف نکنید مگر بخواهید دادهٔ دمو از نو ساخته شود.
- بدون `MAND_APPROVER_KEY` سرویس بالا می‌آید اما فعال‌سازی کمپین بسته است (401).
- `ENABLE_LIVE_SENDS` فقط `false` را می‌پذیرد؛ ارسال واقعی SMS/push وجود ندارد.
- پورت را با `-p <host-port>:3000` تغییر دهید؛ `PORT` داخل کانتینر را عوض نکنید مگر healthcheck و mapping را هم هماهنگ کنید.
- برای استقرار عمومی HTTPS و یک reverse proxy لازم است؛ خود ایمیج TLS terminate نمی‌کند.
- ساخت ایمیج را روی میزبان Docker اجرا کنید، نه در محیط توسعهٔ محدود.

### تنظیمات و فعال‌سازی

| متغیر | پیش‌فرض / قرارداد |
|---|---|
| `PORT` | 3000؛ عدد صحیح 1 تا 65535 |
| `MAND_DB_PATH` | `db/mand.sqlite`؛ پوشهٔ والد باید موجود باشد |
| `MAND_APPROVER_KEY` | خالی: عملیات نوشتن بسته است؛ کلید اختصاصی حداقل 32 کاراکتر |
| `MAND_VIEWER_KEY` | اختیاری، متمایز از کلید approver؛ اجازهٔ فعال‌سازی ندارد |
| `ENABLE_LIVE_SENDS` | `false`؛ مقدار دیگری پشتیبانی نمی‌شود و boot را متوقف می‌کند |

کلیدها را فقط از طریق تنظیمات امن استقرار فراهم کنید؛ در Git، لاگ یا گفتگو قرار ندهید. رابط کمپین کلید را فقط برای همان درخواست می‌گیرد و پس از درخواست پاک می‌کند. برای استقرار شبکه‌ای HTTPS الزامی است. APIهای GET فعلاً عمومی و فقط برای دادهٔ مصنوعی‌اند؛ قبل از ورود دادهٔ واقعی، احراز هویت خواندن و جداسازی tenant لازم است.

فعال‌سازی به `Authorization: Bearer …` و `Idempotency-Key` با 8 تا 128 حرف/عدد/خط تیره نیاز دارد. بدون احراز هویت 401، نقش viewer برابر 403، سقف هزینه 422 و تعارض وضعیت/کلید 409 است. پاسخ تکراری همان کلید و actor/cache ثابت می‌ماند. وضعیت روزآمد را از GET کمپین‌ها بگیرید.

هزینهٔ هر مخاطب از `unit_cost` دیتابیس محاسبه می‌شود؛ سقف کمپین و هزینهٔ رزروشدهٔ تجمعی مشتری در یک تراکنش بررسی می‌شوند. گیرندگان holdout هرگز رزرو یا ارسال نمی‌شوند. بودجه‌ها به ریال‌اند. رزرو پس از شکست هم محافظه‌کارانه حفظ می‌شود؛ آزادسازی/تسویه خودکار هنوز وجود ندارد.

چرخهٔ کمپین `draft → queued → sending → sent|failed` است. worker درون همان سرور هر ثانیه صف پایدار را بررسی می‌کند، حداکثر سه تلاش می‌کند و نتیجهٔ هر گیرنده را ثبت می‌کند. `FileAdapter.send(recipient, template, metadata)` خروجی `{status, providerId, error?}` دارد؛ کلید idempotency در metadata است. adapter مرجع رسید یکتا را در جدول `outbox` فایل SQLite ثبت می‌کند. **sent فقط تأیید شبیه‌ساز است، نه تحویل SMS/push واقعی.** adapter واقعی باید idempotency سمت provider را تضمین کند؛ در این نسخه اتصال زنده نداریم.

### قراردادها و تغییرات 0.2.0

- فعال‌سازی بدون کلید و وضعیت قدیمی `active` حذف شدند؛ فراخوان‌ها باید قرارداد بالا را رعایت کنند.
- خطاهای API همیشه `{error: {code, message}}` و دارای `X-Request-Id` هستند؛ stack و اطلاعات محرمانه ارسال نمی‌شود.
- `explanation` در تصمیم، سگمنت و پیشنهاد کمپین شامل `factors: string[]`، `counterfactual: string`، `confidence: null` و `sourceType: synthetic` است. null یعنی اطمینان آماری اندازه‌گیری نشده، نه صفر.
- مقایسه برای هر ردیف `sourceType: estimated`، `sourceDate` و `confidence: null` دارد؛ هیچ برآوردی تأییدشده معرفی نمی‌شود. خود ماند دیگر جزو رقبا محاسبه نمی‌شود.
- فونت خارجی حذف شد؛ UI از فونت سیستم استفاده می‌کند و بدون CDN کار می‌کند.
- CI آستانهٔ 80٪ پوشش خطوط JavaScript بک‌اند را enforce می‌کند، به‌جز فایل‌های تست. SQLite/Python با تست یکپارچه بررسی می‌شود ولی درصد پوشش Python اندازه‌گیری نمی‌شود. محافظت merge نیازمند required کردن check در تنظیمات مخزن است.
- [روش و محدودیت‌های دادهٔ مصنوعی](docs/SYNTHETIC_DATA.md): بازیابی uplift در benchmark تصادفی، نه تأیید مدل تولیدی.

نسخهٔ ۰.۲.۰ موارد Bug A–I پیوست را در محدودهٔ دمو پوشش داد. در ۰.۳.۰ سفر مشتری، کیف پول، مرکز آزمایش و تخصیص‌گر به‌صورت محاسباتی اضافه شدند؛ تایم‌لاین، کتابخانهٔ قالب، export، OpenAPI و اتصال زندهٔ کانال هنوز قابلیت‌های آینده‌اند. تست مرورگری اجرا نشده است.

ساختار اجرا:

- `frontend/` — داشبورد RTL و رابط کاربری
- `backend/` — API و محاسبات تصمیم
- `db/` — نمونه‌دادهٔ مصنوعیِ بدون اطلاعات شخصی واقعی

APIهای موجود:

- `GET /api/health` — زنده‌بودن فرایند
- `GET /api/ready` — سلامت DB و adapter؛ خرابی برابر 503
- `GET /api/overview` — شاخص‌ها و تصمیم‌های پیشنهادی
- `GET /api/segments` — سگمنت‌بندی رفتار کاربران
- `GET /api/campaigns` — کمپین‌های چندکاناله
- `POST /api/campaigns/:id/activate` — تأیید اجرای یک کمپین پیش‌نویس
- `GET /api/report` — گزارش مدیریتی شش‌ماهه
- `GET /api/comparison` — برگهٔ مقایسهٔ رقابتی و شکاف‌ها
- `GET /api/growth` — اسکن بازار، سفر مشتری، هاب کانال، بهینه‌سازی مشوق، مرکز آزمایش و بهترین زمان ارسال

داشبورد شش بخش دارد: تصمیم‌ها، سگمنت‌بندی، کمپین، گزارش، موتور رشد و مقایسهٔ رقابتی.

## اسکن بازار و پنج قابلیت یکپارچه‌شده در 0.3.0

در آذر ۱۴۰۵ ده رقیب بررسی شد: Braze، Iterable، CleverTap، MoEngage، Insider One و Optimove (بین‌المللی) و پیام‌گستر، دیدار، تیکو و وفادار (ایران). برای هر رقیب پنج قابلیت برجسته ثبت شد و فراوانی هر قابلیت در `db/radar.json` محاسبه می‌شود. پنج قابلیت با بیشترین تکرار که ماند نداشت، در این نسخه پیاده شد:

| قابلیت | منبع بازار | پیاده‌سازی ماند |
|---|---|---|
| سازندهٔ سفر و اتوماسیون رفتار | Braze Canvas، MoEngage Flows، پیام‌گستر | `GET /api/growth` → قیف هر مرحله با نرخ تبدیل و درآمد برآوردی |
| هاب اتصال کانال‌ها | همهٔ ده رقیب | ثبت شش کانال شبیه‌سازی‌شده، پوشش کمپین‌های فعلی و هشدار کانال بدون اتصال |
| کیف پول و بهینه‌سازی مشوق | وفادار، Insider، Optimove | تخصیص حریصانهٔ بودجه بر اساس uplift خالص به ازای ریال با سقف تقاضا |
| مرکز آزمایش و سنجش اثر افزایشی | Braze، Iterable، Insider | آزمون z دو نسبتی، p-value، تشخیص SRM و تصمیم اجرا/توقف/ادامه |
| بهترین زمان ارسال و سقف فرکانس | Braze، Iterable، CleverTap، تیکو | انتخاب پنجرهٔ ارسال از نرخ باز شدن و حذف فرکانس مازاد هفتگی |

شخصی‌سازی، تحلیل و پیش‌بینی از قبل در نسخهٔ ۰.۲.۰ بودند و دوباره کلون نشدند. تایم‌لاین تماس، اتصال زندهٔ SMS/push و اجرای سفر در production هنوز پیاده نشده‌اند. همهٔ اعداد این بخش سناریوی مصنوعی‌اند؛ ارزش هر قابلیت نیازمند اعتبارسنجی با دادهٔ شریک است.

منابع بررسی: صفحه‌های عمومی محصول Braze، Iterable، CleverTap، MoEngage، Insider، Optimove و مستندات محصول پیام‌گستر، دیدار، تیکو و وفادار (دسترسی آذر ۱۴۰۵). پوشش رقبا برآورد تحلیلی و `confidence: null` است.

## قابلیت‌های باقی‌مانده

- تایم‌لاین تماس و خدمات مشتری — P2
- اتصال زنده به درگاه SMS/push/WhatsApp و CRM مشتری
- اجرای زمان‌بندی‌شدهٔ سفر مشتری روی دادهٔ واقعی و آزادسازی خودکار رزرو

این موارد در تب «مقایسهٔ رقابتی» با دلیل و ارزش محصول نمایش داده می‌شوند؛ دادهٔ رقبا برآورد تحلیلی است و قبل از تصمیم تجاری باید با مصاحبه و بررسی رسمی اعتبارسنجی شود.
